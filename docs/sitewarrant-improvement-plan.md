# SiteWarrant --- план изменений

**Целевая концепция:** развить SiteWarrant из инструмента разового
аудита в AI Website Quality Engineer: систему, которая обнаруживает
проблемы, объясняет их причины, предлагает безопасные исправления,
проверяет результат и отслеживает качество сайта во времени.

План составлен с применением принципов [Planning and Task Breakdown от
Addy
Osmani](https://github.com/addyosmani/agent-skills/blob/main/skills/planning-and-task-breakdown/SKILL.md):
сначала изучить существующую архитектуру, определить зависимости,
разбить работу на небольшие задачи с критериями приёмки и проверками, а
затем выполнять их поэтапно.

> Это план изменений, а не указание переписывать уже существующие
> компоненты. Перед реализацией нужно сверить каждую задачу с текущим
> состоянием репозитория и существующими планами.

## 1. Исходное состояние и предположения

По описанию проекта и существующей документации часть возможностей уже
реализована:

-   обход страниц и сбор технических измерений;
-   специализированные AI-агенты для разных направлений аудита;
-   проверка доказательств для AI-находок;
-   объединение проблем по первопричинам;
-   benchmark на искусственных тестовых сайтах;
-   ограниченный набор автоматических исправлений;
-   повторный аудит и поиск регрессий;
-   учёт использования токенов и стоимости;
-   веб-интерфейс и базовая авторизация.

Перед началом работ необходимо перепроверить эти сведения по актуальному
коду, тестам, `AGENTS.md`, `docs/PLAN.md` и каталогу `.agents/plans`.

### Основные проблемы и возможности для развития

1.  **Надёжность выполнения аудитов.** Если фоновые задачи выполняются
    внутри процесса API, перезапуск процесса может прервать аудит или
    оставить некорректный статус.
2.  **Реалистичность benchmark.** Искусственные сайты полезны для
    регрессионных тестов, но не доказывают качество анализа произвольных
    реальных сайтов.
3.  **Проверка пользовательских сценариев.** Эвристический UX-анализ
    стоит дополнить реальным выполнением сценариев в браузере.
4.  **Безопасность исправлений.** Расширять автоматическое исправление
    следует только вместе с изоляцией, проверкой патчей и повторным
    аудитом.
5.  **Мониторинг качества.** Разовые аудиты полезно дополнить сравнением
    результатов во времени и регулярными проверками.

## 2. Целевая архитектура продукта

Предлагаемый жизненный цикл:

1.  **Discover & Audit** --- обнаружение страниц, сбор измерений и
    анализ.
2.  **Evidence & Validation** --- проверка доказательств, достоверности
    и приоритетов.
3.  **Remediation** --- рекомендации и подготовка исправлений.
4.  **Verification** --- применение патчей в изолированной среде,
    повторный аудит и регрессионные проверки.
5.  **Monitoring** --- история аудитов, обнаружение регрессий и
    регулярные проверки.

Архитектурный принцип: детерминированные инструменты собирают измерения;
AI интерпретирует их и предлагает решения; валидатор проверяет выводы;
изменения исходного кода проходят безопасную проверку до принятия
пользователем.

### Этап 1. Надёжность и масштабируемость аудитов

неконтролируемому дублированию результатов.

**Проверки:** - Интеграционный тест с принудительным завершением
процесса. - Тест конкурентного выполнения. - Тест восстановления после

**Критерии приёмки:** - \[ \] У каждой задачи есть однозначный статус. -
\[ \] Недопустимые переходы отклоняются. - \[ \] Ошибки и причины
завершения сохраняются. - \[ \] Повторный запрос не создаёт случайные
дубликаты. - \[ \] Frontend корректно отображает все состояния.

**Проверки:** API integration tests, frontend tests, тесты переходов
состояний.

**Зависимости:** Task 1.1.\
**Оценка:** M.

#### Task 1.3 --- Добавить достоверный прогресс выполнения

**Работы:** - Показывать количество обнаруженных и обработанных
страниц. - Отображать состояние этапов и агентов, если оно доступно из
реального состояния выполнения. - Показывать ошибки и частично

**Критерии приёмки:** - \[ \] Прогресс отражает фактическое состояние, а

**Проверки:** E2E-тест запуска аудита и обновления страницы во время

**Зависимости:** Task 1.2.\

**Контрольная точка 1:** - \[ \] API и исполнитель работают

Нет двойного выполнения одной задачи. - \[ \] Интерфейс показывает
корректный статус и прогресс. - \[ \] Стандартные проверки проекта

**Архитектурное примечание:** перед Task 1.1 выбрать механизм очереди.
Сначала оценить уже используемые PostgreSQL и Redis. Не добавлять новую
инфраструктурную зависимость без обоснования и согласования.

### Этап 2. Качество обнаружения проблем на реальных сайтах

**Приоритет:** P0\
**Цель:** измерить качество системы на сайтах, не созданных специально
под известные правила.

#### Task 2.1 --- Создать benchmark реальных сайтов

**Работы:** - Подобрать репрезентативные сайты: e-commerce, SaaS, блоги,
корпоративные сайты, SPA и landing pages. - Зафиксировать дату и условия
получения каждой страницы. - Организовать независимую экспертную
разметку. - Добавить страницы без известных проблем для измерения ложных
срабатываний. - Хранить benchmark отдельно от искусственного корпуса.

**Критерии приёмки:** - \[ \] Есть отдельный датасет реальных сайтов. -
\[ \] Зафиксированы версия или дата получения и условия проверки. - \[
\] Разметка имеет описание и критерии. - \[ \] Есть чистые примеры для
оценки false positives. - \[ \] Результаты можно воспроизвести в
пределах зафиксированных условий.

**Проверки:** повторный запуск eval, проверка воспроизводимости,
сравнение precision, recall и false-positive rate.

**Зависимости:** Task 0.1.\
**Оценка:** M.

#### Task 2.2 --- Развить объяснимую оценку достоверности находок

**Работы:** - Использовать проверяемые факторы: DOM-элемент, измерение,

**Критерии приёмки:** - \[ \] Для находки доступны объяснимые основания

**Проверки:** validator unit tests, regression tests, eval comparison.

**Зависимости:** Task 2.1.\
**Оценка:** M.

**Варианты обратной связи:** - проблема подтверждена; - ложное

**Проверки:** API tests, тесты сохранения обратной связи и аналитики на

### Этап 4. Развитие автоматического исправления

**Приоритет:** P1\
**Цель:** расширить набор исправлений, не снижая безопасность и

#### Task 4.1 --- Расширить каталог поддерживаемых исправлений

**Критерии приёмки:** - \[ \] Для каждого правила описан алгоритм. - \[
\] Исправление основано на подтверждённой находке. - \[ \] Для каждого
правила есть fixture. - \[ \] Существующая функциональность не
удаляется. - \[ \] Неподдерживаемые случаи явно отклоняются.

**Проверки:** unit tests для правил и integration tests на
fixture-сайте.

**Зависимости:** Task 2.1.\
**Оценка:** M.

#### Task 4.2 --- Усилить проверку безопасности патчей

**Предлагаемый процесс:**

`Generate Patch → Validate → Apply to Copy → Re-audit → Compare → Approve`

**Критерии приёмки:** - \[ \] Патчи применяются только к ожидаемым

Невалидный diff отклоняется. - \[ \] Проверка выполняется в
изолированной копии. - \[ \] Повторный аудит выявляет регрессии. - \[ \]
Оригинальный проект не изменяется до подтверждения пользователя.

**Проверки:** тесты повреждённых и конфликтующих патчей, path traversal

**Зависимости:** Task 4.1.\
**Оценка:** M.

**Критерии приёмки:** - \[ \] Доступ ограничен выбранным репозиторием. -

### Этап 5. История и мониторинг качества

**Приоритет:** P1\
**Цель:** превратить разовый аудит в постоянный контроль качества сайта.

#### Task 5.1 --- Добавить сравнение аудитов во времени

**Критерии приёмки:** - \[ \] Можно сравнить два аудита одного сайта. -
\[ \] Отображаются новые, устранённые и оставшиеся проблемы. - \[ \]
Проблемы группируются по первопричинам. - \[ \] Учитываются версии
правил и агентов. - \[ \] Несопоставимые результаты не выдаются за

**Проверки:** API tests, regression tests и сравнение сохранённых

**Зависимости:** Task 0.1.\
**Оценка:** M.

#### Task 5.2 --- Создать Dashboard динамики качества

**Показатели:** - критические проблемы; - новые и исправленные

## 9. Итоговая рекомендация

Не стоит начинать с добавления новых AI-агентов или большого количества
проверок. У SiteWarrant уже есть интересная техническая основа.

Наибольшую ценность дадут три направления:

1.  **Надёжность:** аудит не теряется и корректно восстанавливается
    после сбоев.
2.  **Достоверность:** качество обнаружения доказано на независимых
    реальных сайтах.
3.  **Действие:** система безопасно исправляет проблемы и проверяет
    результат.

Именно эти улучшения могут превратить SiteWarrant из интересного
инструмента аудита в полноценного AI Website Quality Engineer.

## 1. Допущения, принятые без вопросов

Правьте сейчас, дальше беру их как есть:

1. Один разработчик, 8 недель вечерами ≈ 10 ч/неделю ≈ 80 ч; оценка трудозатрат, не обещание срока.
2. Один репозиторий: `api/` (Python 3.12) + `web/` (Next.js), не два репозитория и не монорепо-тулинг.
3. Аудируются только публичные страницы без авторизации; логин-стены, SPA за авторизацией и капчи — вне MVP.
4. Идентификация пользователя в MVP — нет аккаунтов; публичное демо с rate limit и локальный CLI.
5. LLM-провайдер один, две модели: дешёвая для интерпретации наблюдений, сильная для Chief Auditor и vision.
6. PostgreSQL + pgvector как единственное хранилище фактов; артефакты (HTML, скриншоты) — файлы, в БД только ключи.
7. Демо-стенд — на существующем VPS (`46.149.68.8`, проекты в `/app/`), не на домашнем сервере.
8. Метрики качества считаются только по размеченному бенчмарку, а не по «мнению» на живых сайтах.

## 2. Цель и пользователь

**Что строим.** Аудитор качества сайта, который доказывает каждую претензию замером, сводит симптомы
к одной первопричине и подтверждает исправление повторным замером.

**Кому.** Владелец сайта без штатного QA, фрилансер-разработчик, SEO-специалист, небольшое агентство.

**Как выглядит успех MVP.**

- По URL получается отчёт: до 100 страниц, 8 направлений, каждая находка с уликой и рекомендацией.
- Один и тот же дефект не дублируется: cookie-баннер поверх CTA на мобильном даёт один root cause
  с четырьмя симптомами, а не четыре независимые записи.
- На размеченном наборе опубликованы precision, recall, false-positive rate с указанием знаменателей.
- После правки сайта есть сравнение «было/стало» с явным списком закрытых, оставшихся и новых находок.
- Всё это воспроизводится двумя командами на чистой машине.

**Чем не является.** Не замена Lighthouse, Screaming Frog или Siteimprove. Ценность — в объединении
фактов, интерпретации, поиске связей и контроле исправления, а не в собственном движке замера контраста.

## 3. Словарь: finding, evidence, root cause

Разделение на четыре уровня — главное архитектурное решение проекта, и на нём держится вся измеримость.

| Понятие | Кто производит | Что это | Хранится |
| --- | --- | --- | --- |
| Observation | детерминированный инструмент | сырой факт с числом, DOM-путём или заголовком: `contrast(3.12, need 4.5)`, `HSTS отсутствует`, `LCP 4210 ms` | `observations` |
| Finding | агент + валидатор | трактовка факта: что сломано, кого задевает, как чинить | `findings` |
| Root cause | Chief Auditor | общая причина, к которой сведены несколько симптомов | `root_causes` |
| Fix | отдельный шаг | предложение правки, применённое или отклонённое | `fixes` |

**Finding** содержит: `rule_id`, категорию, severity, заголовок, объяснение, оценку влияния по трём осям
(конверсия / SEO / UX, шкала 0–3), `suggested_fix`, и **минимум одну улику** с идентификатором observation.

**Severity** — четыре значения, фиксированные определения, чтобы разметка не расплывалась:

| Severity | Определение | Пример |
| --- | --- | --- |
| `blocker` | пользователь не может выполнить основное действие или данные небезопасны | форма отправляется без валидации; mixed content на оплате |
| `major` | основное действие выполнимо, но с заметной потерей (доступность, скорость, индекс) | контраст ниже 3:1 у CTA; LCP 4.2 c; нет H1 |
| `minor` | шум для части пользователей или упущенный рост | длина meta description 190 симв.; alt пустой у декоративной картинки |
| `info` | наблюдение без требуемого действия | 3 внешних шрифта вместо 1 |

## 4. Метрики и как они считаются

Всё считается скриптом по JSON-результатам, не глазами. Ненулевой знаменатель — условие публикации числа;
нулевой знаменатель даёт `null`, а не `0`.

| Метрика | Формула | Что доказывает |
| --- | --- | --- |
| `precision` | TP / (TP + FP) | как часто находка настоящая |
| `recall` | TP / gold_labels | сколько размеченных дефектов найдено |
| `false_positive_rate` | FP / (TP + FP) | цена шума для пользователя |
| `duplicate_rate` | находки, у которых есть другая с той же парой (страница, rule_id, элемент) / все находки | работает ли дедупликация |
| `dedup_reduction` | 1 − итоговых находок / сырых кандидатов агентов | сколько шума снял Chief Auditor |
| `pages_audited` | число страниц в аудите | охват |
| `cost_per_100_pages` | 100 × суммарная стоимость / страниц (медиана по сайтам) | экономика |
| `median_duration` | медиана времени аудита по бенчмарку | практическая пригодность |
| `fix_acceptance_rate` | принятых правок / предложенных | полезность рекомендаций |
| `regression_free_fix_rate` | повторных аудитов без новых blocker и major / применённых правок | безопасность правок |

**Сопоставление находки с эталоном (TP/FP/FN).** Детерминированное, без суждений модели:

1. `page_key(url)` = host + путь без завершающего слеша, query и hash отбрасываются.
2. Finding сопоставляется метке (gold label), если совпал `page_key`, совпал `rule_id` и путь элемента
   из улики содержит селектор метки (пустой селектор — совпадения по странице и правилу).
3. Одна метка закрывается не более чем одной находкой; вторая находка на ту же метку — FP.
4. Метки без `rule_id` (новые, не описанные правилом дефекты) идут в отдельную подвыборку `novel`,
   из precision/recall исключаются и оцениваются вручную по рубрике 0/1/2.

**Честность замеров производительности.** LCP и CLS измеряются в лаборатории и **отличаются от поля**;
INP в лаборатории не измеряется вообще, поэтому используется TBT как прокси и в отчёте он так и назван —
«TBT (прокси INP)». Числа производительности берутся медианой из 3 прогонов: один прогон на VPS шумит.

**Оценка направления (продуктовая, не метрика качества).**
`score = max(0, 100 × (1 − penalty / 40))`, где `penalty = Σ весов находок / страниц`,
веса: blocker 8, major 3, minor 1, info 0.25. Формула документируется в интерфейсе; для evals она не используется.

## 5. Границы MVP (scope)

**Входит.** 8 направлений с разной глубиной, 5–10 сайтов и 50–100 страниц в бенчмарке, 3 разрешения
(390 / 768 / 1440), отчёт с уликами, дедупликация и первопричины, повторный аудит, evals, cost accounting,
публичное демо, инженерный отчёт.

| Направление | Глубина MVP | Чем меряем |
| --- | --- | --- |
| SEO | глубокая | собственные проверки по DOM + граф внутренних ссылок |
| Accessibility | глубокая | axe-core + ручные правила WCAG 2.2 AA поверх него |
| Performance | глубокая | Lighthouse (Node CLI) + CDP-метрики |
| UX | эвристический AI-анализ | наблюдения о навигации, CTA, формах + интерпретация |
| UI | vision по скриншотам | скриншоты и кропы элементов + геометрия из DOM |
| Responsive | три разрешения | переполнение, перекрытия, размеры touch-целей |
| Security | пассивные проверки | заголовки, TLS, cookies, mixed content |
| Conversion | эвристическая оценка | видимость value proposition, CTA, доверие, трение |

**Не входит в MVP (non-goals).** Аккаунты и биллинг; сканирование за авторизацией и обход капч;
автоматическое открытие PR с правками в чужих репозиториях; мобильные приложения и браузерные расширения;
собственный движок рендеринга; PDF-экспорт; локализация интерфейса; сравнение с конкурентами по фичам.
Отдельно: UX и Conversion в MVP — эвристика и оценка, и в отчёте они помечены как эвристика,
а не как измерение.

## 6. Архитектура

### Поток аудита

```
URL ──▶ cluster_agent
        └ crawl → discovery (robots, sitemap, BFS) → page templates
             └ per page: http_probe, dom_probe, axe, lighthouse, screenshots (3 viewports), occlusion
                  └ observations (детерминированные факты) + artifacts
                       └ 8 аудиторских агентов (MCP tool-calling, бюджет на агента)
                            └ candidate findings + evidence refs
                                 └ validator: схема, обязательная улика, цитата правила
                                      └ Chief Auditor: dedup → root causes → приоритет → вклад в бизнес
                                           └ report.json + UI
                                                └ fixes → re-audit → diff (закрыто / осталось / новое)
```

### Железные инварианты

1. **Агент не вычисляет факты.** Контраст, заголовки, тайминги, переполнение считают инструменты.
   Агент читает `observations` и ссылается на них. Попытка агента утверждать число, которого нет
   в observations, отбивается валидатором.
2. **Нет улики — нет находки.** Валидатор отклоняет finding без `evidence[].observation_id`,
   указывающего на существующую запись в рамках того же аудита.
3. **Причина группируется детерминированно.** Ключ кластера — (общий layout-компонент, общий DOM-предок,
   семейство правила). LLM пишет только объяснение и оценку влияния, но не решает, что с чем схлопнуть.
4. **Кросс-доменный кластер обязан быть кросс-доменным.** Группа получает статус root cause, только если
   симптомы пришли минимум из двух категорий; иначе это одна находка, а не причина.
5. **Версия агента — хеш.** `agent_version` = sha256 от (промпты, корпус правил, id моделей, конфиг инструментов).
   Любое изменение промпта — новая версия, которую можно сравнить с предыдущей на бенчмарке.

### Решения с «почему»

| Решение | Почему так |
| --- | --- |
| Python + FastAPI сзади, Next.js спереди | вся экосистема замера (axe-core, Lighthouse, CDP, Playwright) ближе к Python-оркестрации; фронт не участвует в замерах и может быть тонким |
| Собственный crawler на httpx + Playwright, без Scrapy | нужен контроль над JS-рендерингом, кэшем и SSRF-защитой на уровне запроса; Scrapy тянет свой планировщик и мешает единой трассировке |
| MCP как настоящий протокол, а не декорация | оркестратор — MCP-клиент, инструменты — MCP-сервер; сторонний агент может подключиться к тем же инструментам, и это проверяемо |
| Локальный фикстур-сайт с заложенными дефектами в CI | сетевые тесты против чужих сайтов флакают; гейт в CI должен быть детерминированным |
| pgvector для корпуса правил вместо отдельной векторной БД | один Postgres на всё, меньше инфраструктуры; корпус — сотни чанков, этого хватает |
| Стоимость считается по прайс-таблице, и параллельно копятся токены и вызовы | на плоском тарифе счёта за прогон нет; тарифо-независимые величины (токены, вызовы, время) остаются честными |
| Три разрешения жёстко, не «адаптивно» | сравнение аудитов между версиями требует одинаковых условий замера |
| Один LLM-провайдер, две модели | дешевле и проще считать; сильная модель только там, где она меняет результат |

### Агенты и их входы

Все восемь агентов — один цикл с разным промптом, набором правил и лимитами. Лимит по умолчанию:
12 вызовов инструментов, 60k токенов, 180 с. Падение агента не роняет аудит: отчёт помечается `partial`.

| Агент | Вход | Ключевые инструменты | Что обязан выдать |
| --- | --- | --- | --- |
| SEO | граф ссылок, метаданные, JSON-LD | `dom_probe`, `http_probe`, `rules_lookup` | находки по индексации, canonical, sitemap, заголовкам |
| Accessibility | axe violations, порядок табуляции | `dom_probe`, `rules_lookup` | находки с цитатой критерия WCAG |
| Performance | Lighthouse, CDP-трейс | `lighthouse`, `resources` | находки с числом и источником числа |
| Security | заголовки, TLS, cookies | `http_probe` | пассивные находки, без активных атак |
| UI | скриншоты 3 viewport + кропы + геометрия | `vision`, `dom_probe` | визуальные находки с кропом и DOM-путём |
| UX | структура страниц, формы, кнопки | `dom_probe`, `vision` | эвристические находки с явной пометкой эвристики |
| Responsive | переполнение, перекрытия, touch-цели | `dom_probe`, `occlusion`, `vision` | находки по конкретному viewport |
| Conversion | CTA, value proposition, доверие, формы | `dom_probe`, `vision` | находки с оценкой влияния на конверсию |
| Chief Auditor | все кандидаты + наблюдения | чтение БД | кластеры, приоритет, обоснование, отчёт |

## 7. Модель данных

Postgres 16 + pgvector, миграции Alembic. Артефакты — файлы на диске, в БД ключи.

```
sites(id, url, created_at)
audits(id, site_id, status, config jsonb, agent_version, parent_audit_id,
       started_at, finished_at, pages_count, tokens_in, tokens_out, llm_calls, cost_estimate_usd)
pages(id, audit_id, url, template_id, depth, status_code, render_mode)
snapshots(id, page_id, viewport, html_key, dom_key, screenshot_key, captured_at)
observations(id, page_id, viewport, tool, rule_ref, kind, payload jsonb)
findings(id, audit_id, page_id, rule_id, category, severity, title, summary,
         impact_conversion, impact_seo, impact_ux, confidence, root_cause_id, agent)
finding_evidence(id, finding_id, observation_id, kind, excerpt)
root_causes(id, audit_id, page_id, cause_kind, summary, rationale)
fixes(id, finding_id, kind, body, status, applied_at)
audit_diffs(id, base_audit_id, new_audit_id, closed, opened, persisting, regressions)
rules(id, source, code, title, body, tags text[], embedding vector(1024))
llm_calls(id, audit_id, agent, model, tokens_in, tokens_out, usd_estimate, latency_ms, trace_id)
label_sets(id, name, created_at)
labels(id, label_set_id, page_key, rule_id, selector, severity, note)
eval_runs(id, label_set_id, agent_version, metrics jsonb, report_key)
feedback(id, finding_id, action, note, created_at)   -- accept/reject для самоулучшения
```

Почему так: `observations` отдельно от `findings` — чтобы можно было пересобрать находки новым промптом
без повторного сканирования и чтобы precision считалась на неизменных фактах. `labels` отдельно от
`findings` — чтобы метки жили дольше любого прогона и сравнивались между версиями агента.

## 10. Стиль кода

Функциональный стиль с обеих сторон: данные приходят и уходят моделями, логика — функции, классы
только там, где их диктует фреймворк или протокол. Имена универсальные, по предметной области,
без `Manager`, `Helper`, `Processor`. Промпты — на английском, в отдельных файлах, версионируются как код.

```python
# api/app/tools/contrast.py
def contrast_ratio(foreground: Rgb, background: Rgb) -> float:
    light, dark = sorted((relative_luminance(foreground), relative_luminance(background)), reverse=True)
    return (light + 0.05) / (dark + 0.05)


def observations_for_page(page: PageDom) -> list[Observation]:
    return [
        contrast_observation(node)
        for node in text_nodes(page)
        if resolved_contrast(node) < threshold_for(node)
    ]
```

```ts
// web/src/lib/findings.ts
export const groupByRootCause = (findings: Finding[]): RootCauseGroup[] =>
  Object.entries(
    findings.reduce<Record<string, Finding[]>>((groups, finding) => {
      const key = finding.rootCauseId ?? "unassigned";
      return { ...groups, [key]: [...(groups[key] ?? []), finding] };
    }, {}),
  ).map(([rootCauseId, items]) => ({ rootCauseId, items }));
```

## 11. Тестирование и evals

**Уровни.**

- Unit — инструменты замера на записанных DOM-фикстурах: контраст, длины заголовков, парсинг заголовков,
  определение переполнения. Сети нет.
- Integration — полный проход на локальном фикстур-сайте (статичный сайт в контейнере с 12 заранее
  заложенными дефектами: контраст, отсутствующий alt, перекрытие CTA баннером, медленный ресурс, отсутствие HSTS).
- Agent tests — прогон агента на записанных observations с записанными ответами LLM (кассеты), без вызовов сети.
  Проверяется: соблюдение схемы, обязательная улика, отсутствие выдуманных observation_id.
- Evals — бенчмарк на реальных сайтах, запускается вручную и ночью, результаты коммитятся как JSON.
  Гейтом в CI он не является: чужие сайты меняются.

**Фикстура — источник истины для CI.** Ожидания фиксируются в `benchmark/fixtures/expected.json`;
расхождение — падение теста. Это единственный способ заметить, что новый промпт стал врать.

**Бенчмарк.** 8 сайтов, ~100 страниц: 5 своих и знакомых (включая этот проект и портфолио), 3 публичных
с устойчивой разметкой. Разметка вручную по направлениям, полный пере-разбор раз в неделю.
Для каждой страницы фиксируется `page_key`, чтобы изменения URL не ломали счёт.

  попадает в `regressions` как `A11Y-LABEL`.
- Verify: `uv run sitewarrant reaudit <audit_id> --against-report old.json`

### P7 — наблюдаемость, стоимость, самоулучшение, демо (неделя 7–8) — **выполнено, кроме публичного стенда**

Трассы от аудита до вызова LLM, учёт токенов и стоимости, петля обратной связи, полный CI,
демо на VPS, инженерный отчёт.

- Трассы: `app/telemetry.py` — спан на аудит → страницу → агента → вызов инструмента → вызов LLM,
  идентификаторы в терминах OTel, файл `trace.jsonl` в артефактах аудита, `trace_id` в `llm_calls`.
  SDK OTel не подключён намеренно: один процесс на аудит, дерево маленькое, а регистратор спанов,
  который не может уронить аудит, здесь важнее экспортёра.
- Стоимость: `pricing/pricing.yaml` с версией и источником; `cost_estimate_usd` в `llm_calls`,
  в аудите и в отчёте, разбивка по агентам, версия прайса пишется в `audits.config`.
  Токены и число вызовов — измеренные величины, стоимость — оценка, и отчёт это пишет рядом.
- Бюджет: `SITEWARRANT_AUDIT_COST_LIMIT_USD` (по умолчанию 0.25); при достижении агент
  останавливается со статусом `budget_exceeded`, оставшиеся агенты помечаются как не запускавшиеся.
- Петля: `sitewarrant prompt-check --baseline old.json --candidate new.json` — правка промпта
  принимается только если precision не упал и FP-rate не вырос; разные корпуса не сравниваются.
- Демо: `infra/demo.yml` + `api/Dockerfile`; порт наружу не публикуется, публичный URL — за
  прокси с TLS. **Стенд на VPS не поднят:** нужен домен/DNS и секреты владельца (вопрос §17.3).
- Отчёт: `docs/ENGINEERING_REPORT.md` с числами из `evals/runs/`.
- Acceptance: разбивка стоимости и токенов по агентам есть в отчёте; гейт промптов отбивает
  регрессию precision (`tests/test_prompt_gate.py`); демо по публичному URL **не подтверждено** —
  стенд не развёрнут (нужен VPS-домен владельца).
- Verify: `curl` демо-эндпоинта на поднятом стеке, `gh run list` по всем workflow, наличие
  `docs/ENGINEERING_REPORT.md` с числами из `evals/runs/`

Порядок жёсткий: P2 не начинается без P1, потому что наблюдения без обхода неполны; P5 не начинается
без P3, потому что оценивать нечего. P6 может быть урезан до рекомендаций без diff, если график горит
(не понадобилось: diff для пяти правил сделан).

## 13. Наблюдаемость и стоимость

- OTel: спан на аудит → страницу → агента → вызов инструмента → вызов LLM; `trace_id` пишется в `llm_calls`.
- Каждый вызов LLM: модель, токены вход/выход, латентность, оценочная стоимость, агент, аудит.
- `pricing.yaml` версионируется; версия прайса сохраняется в аудите, чтобы старая стоимость не пересчитывалась
  новыми ценами молча.
- Никаких чисел стоимости без пометки: `cost_estimate_usd` — оценка по прайсу; фактические токены и число
  вызовов — измеренные величины.
- Бюджеты: потолок стоимости на аудит в конфиге; при превышении агент останавливается с пометкой `budget_exceeded`.

## 14. Безопасность и изоляция

- Запрет SSRF: резолв DNS → отказ для loopback, private, link-local, multicast; запрос идёт на
  закреплённый IP; каждый редирект (максимум 3) проверяется заново.
- Ограничения: ответ ≤5 МБ, страниц ≤ лимита, таймаут на страницу, конкурентность ≤4, пауза между
  запросами к одному хосту.
- Только GET; никаких авторизационных заголовков; robots.txt соблюдается по умолчанию.
- Браузер в контейнере без доступа к внутренней сети, отдельный сетевой namespace.
- MCP-сервер инструментов не принимает произвольные команды оболочки: только описанные инструменты с валидацией входа.
- В отчётах не сохраняются токены из URL и тела форм.

## 15. Риски

| Риск | Признак | Мера |
| --- | --- | --- |
| LLM выдумывает находки | точность падает, улики не резолвятся | валидатор «нет observation_id — нет находки», обязательный тест на подсунутую выдумку |
| Бенчмарк субъективен | два разбора одной страницы расходятся | четыре severity с определениями, правило сопоставления, пере-разбор раз в неделю, разногласия в `note` |
| Производительность флакает | LCP прыгает между прогонами | медиана из 3, фиксированные условия, числа perf вне CI-гейта |
| Скоуп 8 направлений размывает работу | агенты не доведены, метрик нет | глубина по таблице §5; UX и Conversion явно помечены эвристикой; при нехватке времени режется P6, не P5 |
| Стоимость на 100 страниц выходит за бюджет | стоимость аудита растёт с каждой страницей | лимиты на агента, дешёвая модель на интерпретации, наблюдения кэшируются, повторный прогон не пересканирует |
| Crawler попадает в ловушку (бесконечная пагинация) | аудит не завершается | лимиты страниц и глубины, отсечение похожих URL, нормализация ключей |
| Демо на VPS не видит западные LLM API | 403 при обращении к провайдеру | провайдер, доступный с VPS; вопрос §17.1 |
| 8 недель вечерами не хватает | фазы едут на 1–2 недели | вехи-срезы, обязательный работающий отчёт уже после P0; урезание P6 |

## 16. Definition of Done

MVP готов, когда все пункты проверены прогоном:

1. Аудит публичного сайта на 50+ страниц даёт `report.json` со всеми полями из §3.
2. На бенчмарке 8 сайтов и 100+ страниц посчитаны precision, recall, false-positive rate, duplicate rate,
   cost per 100 pages, median duration — каждое с указанным знаменателем и датой.
3. Каждая находка в отчёте имеет минимум одну улику, и валидатор доказуемо отбивает находки без неё.
4. Кейс «баннер перекрывает CTA на мобильном» сведён в один root cause с симптомами из 2+ категорий.
5. Повторный аудит показывает закрытые, оставшиеся и новые находки; список регрессий формируется.
6. Две версии агента сравнены в инженерном отчёте, разница объяснена.
7. Демо доступно по публичному URL и делает аудит без ручных действий.
8. `README.md` и `AGENTS.md` соответствуют реальным командам и реальным числам; ни одного числа без источника.
9. CI зелёный на чистой машине: `make check` и сборка образов.

## 17. Открытые вопросы

Решения не приняты. Ответ — номерами, например «1а, 2б».

1. **Провайдер LLM для демо.** Решено владельцем 2026-11-12: OpenCode Zen Go (`https://opencode.ai/zen/go/v1`),
   модель `deepseek-v4.1-flash` для всех агентов. Вариант (б), два провайдера за роутером, отклонён.
2. **Формат исправлений.** (а) текстовая рекомендация для всех находок, diff для пяти детерминированных
   правил — рекомендую; (б) diff для всех находок — высокая цена ошибочного патча и рост объёма P6.
3. **Демо-стенд.** (а) существующий VPS рядом с остальными проектами — рекомендую; (б) отдельный
   сервер — чище по ресурсам, но новая инфраструктура и отдельные деньги.
4. **Что считать страницей в бенчмарке.** (а) только HTML-документы 200; (б) включать 3xx-цепочки и
   параметризованные URL — рекомендую (а), иначе метрики поедят редиректы.
5. **Глубина vision-аудита.** (а) только 3 полных скриншота страницы на viewport — дёшево, рекомендую;
   (б) плюс кропы найденных проблемных элементов — точнее, но заметно дороже по токенам.
6. **Открывать ли исходный код демо-версии агентов публично.** (а) весь репозиторий публичный —
   рекомендую для портфолио; (б) публичный, но промпты и корпус правил закрыты — противоречит идее
   «воспроизводимый аудит».
